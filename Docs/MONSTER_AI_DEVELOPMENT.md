# 从最新上游实现 V208 怪物 AI 规则

在 GM 后台添加「怪物 AI」，允许管理员按全局、单图和怪物等级阶段设置血量、防御、攻击、移动速度、攻击速度、攻击欲望倍率。保存规则后，下次进入副本读取新配置，正在进行的副本继续使用进图时的配置。日常调参无需重启游戏或服务端。

## 开发起点

使用 [ServerS5A3](https://github.com/Cec1c/ServerS5A3) 和 [PurpleMagic](https://github.com/Cec1c/PurpleMagic) 当前上游默认分支的干净源码。记录两个仓库的 HEAD。本文中的新增文件名用于指导实现，首次开始开发时可自行创建。实际目录随上游变动时，按文中给出的路由、类型、函数和封包语义查找等价入口。

准备项目指定的 Go、Node.js 和 MariaDB，以及 Windows 上的 MSVC x86、Python 和 pefile。客户端构建还需要与你的发行渠道匹配的原版 V208 EXE 和 PVF。第 4 节给出的地址适用于指定摘要的 EXE，其他版本需要重新定位和核对。执行顺序为规则与存储、管理 API 与页面、服务端进图、客户端接收与属性写入、部署验收。

### 可以直接交给 AI 的任务

> 从我提供的两个干净上游仓库出发，按本文实现 GM 怪物 AI 规则。先定位上游等价入口，再分层实现和验证。以实际部署链路为准，覆盖完整和缓存 START_MAP、组队快照、保存后重进生效以及客户端版本校验。提交实现文件和验证结果，说明当前上游相对本文的差异。

## 1. 定义规则和保存接口

在 ServerS5A3 的 `go-server/internal/modules/dnf/monster/` 新建 `tuning.go`，定义规则、校验和匹配逻辑。全局规则最多一条。单图按实际房间地图 ID 匹配，同一 ID 最多一条。等级按怪物生成等级匹配，范围为 1–255，包含两端，区间不可交叠。优先级为 **单图 > 等级阶段 > 全局**，命中后取该条规则的整组六项倍率。无匹配项时六项均为 1。

保存时要求六项显式填写、均为有限数值。血量必须大于 0，其余可以为 0。攻击和防御各自同时作用于物理和魔法属性。对外 API 使用 `GET /api/v1/monster-tuning` 和 `POST /api/v1/monster-tuning`。先 GET 取得当前 `revision`，保存时提交该版本号及完整规则列表。以下示例中的版本号应替换为读取值。

```json
{
  "revision": 0,
  "rules": [
    {
      "scope": "global",
      "multipliers": {
        "hp": 2,
        "defense": 1.5,
        "attack": 1.2,
        "moveSpeed": 1,
        "attackSpeed": 1,
        "aggression": 0.8
      }
    }
  ]
}
```

单图使用 `scope: "map"` 和 `mapId`，等级阶段使用 `scope: "level"`、`minLevel`、`maxLevel`。保存空数组可清空规则。在 `dnfbridge/account_security.go` 的数据库初始化流程中创建账户表前缀加 `_monster_tuning` 的表，包含 `id INT PRIMARY KEY`、`rules_json MEDIUMTEXT NOT NULL`、`revision BIGINT UNSIGNED NOT NULL`。以 `INSERT IGNORE` 初始化 ID 1、空数组、版本 0，升级或重启时保留既有数据。使用带旧版本条件的 UPDATE 原子更新并递增版本。版本冲突返回 HTTP 409，前端提示重新读取后再编辑。校验失败返回 HTTP 422。

## 2. 接通 GM 页面和游戏服

1. 在 PurpleMagic 的 `gm-console/src/App.tsx` 注册侧边栏与页面，在 `gm-console/src/pages/MonsterAI.tsx` 新建页面实现读取、新增、删除和保存，复用现有认证请求客户端。规则属于服务端，页面无需先选择角色。
2. 在 PurpleMagic 的 `gateway/internal/services/gmtool` 和 `gm/internal/services/gmtool` 接入 GET 和经写权限中间件保护的 POST，复用各自的 `adminapi` 请求。在两端管理协议的请求与响应分别增加 `monsterTuning` 字段，并沿用现有错误信封。通过游戏服管理接口调用 `monster_tuning` 和 `monster_tuning_save`。按实际部署链检查路由。若独立 GM 经 PlayerGateway 转发，两边都要更新。
3. 在 ServerS5A3 的 `go-server/internal/services/dnfbridge/game_admin_api.go` 分发这两个动作，新建 `monster_tuning_admin.go` 读写数据库。先验证 GM 页面能保存并读回版本，随后验证游戏内属性。两项验证分别覆盖管理链路与战斗链路。

## 3. 在进图时同步规则

在 `dungeon_runtime_state.go` 创建副本运行状态时读取并编译规则，得到该次副本的快照。组队成员使用队长快照，换房间沿用这份快照，再用目标房间地图 ID 匹配单图规则。

新建 `monster_tuning_wire.go` 实现 `appendMonsterTuningTrailer`，从 `dungeon_start_map.go` 的完整进图包和 `dungeon_move_runtime.go` 的缓存房间包调用。无规则快照时原样返回包体。组队快照从 `dungeon_navigation_runtime.go` 的队长入场计划传递。扩展附在 START_MAP（op29）原包体末尾。每行包含起止等级两个字节和六个小端 binary64 倍率，顺序为血量、防御、攻击、移动速度、攻击速度、攻击欲望。连续相同倍率合并成一行，所有行覆盖 0–255。尾部追加四字节小端行数据长度和四字节 ASCII 标记 `MAT1`。

现有实现仅在服务端客户端类型为 `official-24.9` 且设置 `DNFBRIDGE_MONSTER_TUNING=paired-v1` 时加载规则快照。部署时将该开关与支持 MAT1 的客户端配套启用。

## 4. 在 V208 客户端应用倍率

参考上游已有的 `resource-recipes/client-features-native/native/build_candidate.py` 和 `build.bat` 的工具链与 PE 构建模式。在该目录新建 `v208_dungeon_monster.h` 封装封包与怪物布局，再新建 `monster_tuning_v208.cpp` 实现两个入口。原版输入的完整 SHA-256 为 `5ce2ce3f01dacd05a6ce542d088911cc4fceb0f44ffa85dfa3a0886339e7cb5c`。其他 EXE 版本需重新验证布局和入口。

```text
收到 START_MAP：
    清除上一次的倍率快照
    验证 MAT1 尾部和完整等级区间
    扩展有效时加载新快照，并将包体长度恢复为原包体长度
    交回原生 START_MAP 回调

房间怪物创建完成、原生逻辑读取出生血量前：
    校验怪物类型与属性布局
    读取实际怪物等级并查找当前房间倍率
    在四个原生属性块写入最大血量、物理和魔法攻防、移速和攻速
    同步当前血量，将攻击欲望限制为 0–100
    恢复原生执行
```

### V208 入口和布局

以下为 PE32、首选映像基址 `0x00400000` 的虚拟地址。构建器按完整摘要、架构、基址和原字节核对后再修改。

| 位置 | 实现 |
| --- | --- |
| START_MAP 回调注册 `0x02001F84` | 原指针 `0x01FF8D80`。替换为接收适配器。游标在 `0x057F9AD0`，剩余字节数在 `0x057F9AD4`。保存寄存器和标志，解码后尾跳到原回调。 |
| 怪物出生 `0x02628EDD` | 原八字节 `8B 06 8B 90 34 04 00 00`。使用相对跳转接入，`ESI` 为对象。保存寄存器和标志，调用倍率应用函数，再重放 `mov eax,[esi]` 和 `mov edx,[eax+0x434]`，回到 `0x02628EE5`。 |
| 类型与布局 | 检查对象存在，确认对象 `+0xA8` 的种类为 `0x211`，虚表字节偏移 `0x50 / 0x670 / 0x694` 的三个函数地址分别为 `0x02677900 / 0x026D13C0 / 0x026D13F0`。 |
| 属性块 | 对象 `+0x10D0 + i×0x740`，共四块。首块起点存等级。每块相对偏移 `+8` 为最大血量。 |
| 普通属性 | 块内 `+0x2A0` 移动速度、`+0x2B0` 攻击速度、`+0x338` 物攻、`+0x348` 物防、`+0x358` 魔攻、`+0x368` 魔防。 |
| 独立字段 | 对象 `+0x2DD0` 为当前血量，`+0x41D8` 为明文攻击欲望。 |

32 位字段按字段地址低四位选择编解码函数。低四位为 0、4、8、12 时分别使用前四组，其余使用第五组。

| 原生函数 | 地址 |
| --- | --- |
| 32 位读取 | `0x037DF550`、`0x037DF5C0`、`0x037DF630`、`0x037DF6A0`、`0x037DF7F0` |
| 32 位写入 | `0x037DF130`、`0x037DF1B0`、`0x037DF230`、`0x037DF2B0`、`0x037DF010` |
| 64 位血量读取与写入 | `0x037DF870`、`0x037DF090` |

以上函数使用 MSVC x86 `__thiscall`。读取参数依次为字段地址、编码数据地址、输出值地址。写入参数依次为字段地址、输入值地址、编码数据地址。普通属性的编码数据位于字段 `+4`，血量位于字段 `+8`。在游戏线程中操作存活对象。1 倍保留原值。正血量向零截断后限制在 1 到 INT64_MAX，非正血量保持原值。普通属性向零截断并限制在 INT32 范围。

解析 MAT1 时验证原包体至少剩 16 字节，行区非空且是 50 字节的整数倍，长度在剩余包体范围内。校验区间无缺口、无重复且恰好覆盖 0–255，并验证所有倍率。完整校验成功后才启用新快照并缩短原生可读长度。普通包体和无效扩展清除旧快照，原生继续按收到的长度读取。

## 5. 构建和部署

1. 仿照上游构建方式新建 `build_monster_tuning_v208.bat` 和 `build_monster_tuning_v208.py`。C++ 使用 MSVC x86 构建固定基址 `0x06F90000`、无入口和 CRT 依赖的 DLL，导出两个跳转入口。PE 构建器读取其代码和数据节后嵌入原版，保留代码 RX、数据 RW，按虚拟地址定位两处改动。原映像的 `.mailrg`、`.emright`、`.wk855` 若文件和内存都连续且权限一致，可合并节头腾出两个位置。检查末节 `.ctnull` 延伸的零填充恰好接上首个新增节，再更新 PE 映像大小、代码和数据大小及校验和。回读原节数据核对改动范围，输出到新的目录。

   实现构建入口后，在 ServerS5A3 根目录运行，产物为 `DNF-receiver.exe`。

   ```bat
   resource-recipes\client-features-native\native\build_monster_tuning_v208.bat "原版DNF.exe路径" "新的输出目录"
   ```

2. 按部署环境构建游戏服、GM 前端和实际承接 API 的网关或独立 GM 服务。核对待替换的客户端目录、服务端及启动器配置，备份现用文件和签名发布状态。
3. 停止目标进程后切换产物，将候选 EXE 安装为现用 `DNF.exe`。用实际 EXE 和 PVF 摘要更新启动器批准配置，按现有 Hub 发布流程同步发布状态、递增发布序号并用原信任根签名。局域网首次启用时，设置服务端配套开关并启动相关服务。用启动器验证签名、文件摘要、登录和选角。
4. 如 Windows 在进程创建时返回错误 193，先核对 PE 节的映像布局和候选输入版本。本次初版出现过节间映像空隙导致 Windows 拒绝加载，最终构建器通过对齐并扩展末节的虚拟范围修正。发布前应验证 Windows 能加载候选文件。部署失败时恢复备份，并按启动器发布规则发布更高序号的回滚配置。

## 6. 回归与联机验收

在怪物领域包和 dnfbridge 中新增与本文行为对应的规则、存储及封包用例，然后在 `ServerS5A3/go-server` 中运行。数据库用例复用项目现有 MySQL fixture，并确认执行结果没有跳过。

```text
go test ./internal/modules/dnf/monster
go test ./internal/services/dnfbridge -run TestMonsterTuning -v
```

在 `PurpleMagic/gm-console` 执行 `npm test` 和 `npm run build`。使用实际部署的 GM 页面与游戏客户端完成以下验收。

| 操作 | 预期结果 |
| --- | --- |
| 保存全局、单图、等级规则并重新读取 | 六项倍率与版本号匹配，重复或交叠规则被拒绝 |
| 用两份同版本配置先后保存 | 第二次保存返回 409 |
| 设置非 1 倍率后进入副本 | 验证当前和最大血量、物理与魔法攻防、移速、攻速和攻击欲望 |
| 在已进副本时保存新倍率，再退出重进 | 本次副本继续使用原快照，重进后使用新倍率，两个进程都无需重启 |
| 规则重叠命中、换房和组队 | 单图优先，其次等级，最后全局。完整包、缓存包和队友使用正确快照 |
| 清空规则后重进 | 怪物恢复基础数值，玩家属性保持原有行为 |

后台可保存但进图无变化时，依次核对游戏服是否加载快照、op29 是否携带 MAT1、现用 EXE 是否经过签名发布、怪物出生入口是否命中。后台提示接口不存在时，先检查实际转发链中哪一层仍运行旧版本。
